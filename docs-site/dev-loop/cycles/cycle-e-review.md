2. **No handler mutex may be held while calling a driver port.** `ZephyrUartDriver.schedIn` is `guarded` (`lib/fprime-zephyr/.../ZephyrUartDriver.fpp:7`), so the 50 Hz thread holds the driver mutex when it calls `uartRecv`; `$send` and `recvReturnIn` are guarded too (`ByteStreamDriver.fpp`). A guarded `run` that calls `uartSend_out` holds handler → driver while 50 Hz holds driver → handler; rateGroup50Hz is priority 1 and rateGroup1Hz priority 3 (`instances.fpp:31-44`, Zephyr numeric priority passed through, `Os/Task.cpp:48`), so the inversion deadlocks the first time bytes arrive during a 1 Hz tick — only with a board attached, invisible on the host. Do it the FaultManager way (`FaultManager.cpp:161-170`): `uartRecv` stays `guarded`; `run`, `uartReady` and all six commands are `sync`; each brackets its state work with the generated `this->lock()/unLock()` and calls `uartSend_out` only after `unLock()`. The TX frame is a stack-local 39-byte array per send (the shared static array in 3.2 would be raced by the command thread once sends are outside the lock). The host stub counts output-port calls made while locked (copy `actionWhileLocked` from the FaultManager stub) and `test_DriverBoardHandler_Component.cpp` asserts zero.
