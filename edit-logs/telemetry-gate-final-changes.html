What Changed: Telemetry Gating and Requirements Tracking

Edit log entry: 2026-07-29. Base commit 07b6046 ("added requirements traceability matrix") on main; covers the uncommitted work on top of it and the port/telemetry-gate-rtm branch for the washu fork.

A walkthrough of the work added to the PROVES CubeSat flight software, written for readers who do not work in this repository. Three deliverables: (1) a new telemetry gate component that lets the ground turn the satellite's routine data broadcasts off and on, (2) unit tests that run the real flight code on a laptop, and (3) an automatically generated requirements verification matrix, now loaded with the CDH requirements from the CDR and editable from the terminal.

0. Background: what this software is

This repository is the flight software for a PROVES-kit CubeSat. It runs on an RP2350 microcontroller using NASA JPL's F´ (F Prime) framework. In F´, the software is built from small components connected by ports, like blocks in a circuit diagram. One stock component, TlmChan, is the telemetry channel database. Every sensor reading (battery voltage, temperatures, gyro rates) is written into it, and once per second a timer tick tells it to package everything up and push it to the radio for downlink.

1. The problem: no way to stop telemetry transmission

Before this change, that once-per-second tick was wired directly into the telemetry database, so the satellite always broadcast its housekeeping data. There was no command to stop telemetry transmission. That capability is required for RF-quiet operations, licensing constraints, and deployment timing rules. It is requirement CDH-3 from the CDR ("Shall be capable of ceasing transmission on command") and its children CH-L2-13/15/17, which were marked not met at CDR.

Before

The scheduler tick flowed directly into the telemetry database. The only way to stop telemetry was to power off the radio, which would also kill command uplink and warning events.

After

A new component, the Telemetry Gate, sits in the middle of that connection. A ground command opens or closes it. Closed means routine telemetry stops within one second. Commands, acknowledgements, and warning events still flow, so the satellite can always be recovered.

The telemetry path before and after. The gate is the only new element in the path. Everything around it is untouched.

Design decisions worth knowing

  • Defaults to transmitting on any error. If the saved state file is missing, unreadable, or corrupted (checked with a magic header and integrity byte), the gate defaults to ENABLED and raises a warning event. This means a corrupted file can never leave the satellite silent; it keeps transmitting and reports the corruption instead.
  • The command takes effect within one cycle (requirement CH-L2-15, red at CDR). The new state is set in memory first, then saved to flash. If the flash save fails, the command reports an error but the state change still holds, and a warning event says so.
  • A commanded disable survives reboots. This is needed for RF-quiet windows longer than one boot. It is safe because the command link is never gated: the ground can always send ENABLE.
  • While disabled, the gate counts what it dropped (GatedTicks), so operators can see afterwards exactly how long the satellite was silent.

2. Testing flight code without a satellite on your desk

This repository has a rule that unit tests must run on a plain laptop with no F´ framework headers, and F´'s own test-generation tooling is not set up here. As a result, component behavior (commands, ports, events) could not be tested off-hardware at all. Only standalone math and logic files had tests.

Before

To find out whether a component behaved correctly you had to flash a physical board and run radio tests. A logic bug in boot-time state loading could only be found on hardware.

After

A small set of hand-written stand-in classes imitates exactly the framework surface the component touches, and records everything the component does (ticks forwarded, events emitted, command responses). The real, unmodified flight code compiles against these stand-ins and runs under googletest on any laptop, in CI, in seconds.

The test setup: the flight source file is compiled as-is; only its surroundings are simulated.

This matters beyond TelemetryGate: the type stubs, fake file system with fault injection, and recording base class are a reusable pattern. Any future component can copy them to get fast tests of real flight logic.

3. Requirements verification, generated from the code

The team's requirements were in CDR slides, and their verification status was not recorded anywhere. Now the repository generates a Requirements Traceability Matrix (RTM). The RTM lets devs make sure every requirement is covered and keeps track of how each one will be proven, at what level, against which pass criteria, and whether it is currently passing. It is not maintained by hand and is rebuilt from source on every push.

The CDH requirements from the CDR are now in the repository

All 105 requirements from the SCALAR Command and Data Handling CDR deck were transcribed: the 31 top-level requirements (CDH-1 to CDH-31) and all seven L2 groups: Command Handling (20), Telemetry Acquisition (9), Storage (14), Scheduling (7), Mode Management (9), FDIR (9), ADCS Enablement (6). Two of the red CDR items, CH-L2-15 (stop transmission within one cycle) and CH-L2-17 (inhibit telemetry scheduling when disabled), are exactly what the Telemetry Gate implements.

4. What exactly changed, with diffs

Each change below shows the actual lines before and after (red = removed, green = added), what kind of change it is, and which requirements it serves. This is the full substance of the work; everything else in the branch is documentation or build plumbing for these.

4.1 The one rewired connection: inserting the gate into the telemetry path

Type: Feature    Verifies: CDH-3, CH-L2-17, TelemetryGate-2, TelemetryGate-3

This is the core of the whole change. F´ wires components together in a topology file, which serves as the wiring diagram. Before, the once-per-second telemetry tick went straight to the telemetry database (tlmSend) and nothing could stop it. Now it passes through the gate first:

// ReferenceDeployment/Top/topology.fpp (the component wiring diagram)
-      telemetryDelay.runOut -> CdhCore.tlmSend.Run
+      # TelemetryGate sits between the rate divider and TlmChan so it can inhibit
+      # scheduled telemetry downlink when transmission is disabled.
+      telemetryDelay.runOut -> telemetryGate.runIn
+      telemetryGate.runOut -> CdhCore.tlmSend.Run

The gate is registered as a new component instance with its own command and telemetry ID range, verified unused on both repositories:

// ReferenceDeployment/Top/instances.fpp
+  instance telemetryGate: Components.TelemetryGate base id 0x1003C000

4.2 The gating decision

Type: Feature    Verifies: TelemetryGate-2, TelemetryGate-3, TelemetryGate-8, CH-L2-13

New code; this component did not exist before. Every second the scheduler tick lands here, and the entire cease-transmission behavior is this if/else:

// Components/TelemetryGate/TelemetryGate.cpp, runs once per scheduler tick
void TelemetryGate::runIn_handler(FwIndexType portNum, U32 context) {
    if (!this->m_loaded) {          // first tick after boot: restore saved state
        this->loadState();          // from flash, BEFORE the first gating decision
        this->m_loaded = true;
    }

    if (this->m_state == TelemetryTxState::ENABLED) {
        this->runOut_out(0, context);   // pass the tick along: telemetry runs
    } else {
        this->m_gated_ticks++;          // drop the tick: telemetry silent; count it
    }

    this->tlmWrite_TransmitState(this->m_state);   // report own state
    this->tlmWrite_GatedTicks(this->m_gated_ticks);
}

4.3 The command: takes effect next tick, survives a failed save

Type: Feature    Verifies: TelemetryGate-1, TelemetryGate-7, CH-L2-12, CH-L2-15, CH-L2-16

CH-L2-15 (cease within one scheduler cycle) was red at CDR. The fix is the ordering here: memory first, flash second, so the very next tick obeys the command even if the flash write is slow or fails:

// Components/TelemetryGate/TelemetryGate.cpp
void TelemetryGate::SET_TRANSMIT_STATE_cmdHandler(opCode, cmdSeq, txState) {
    this->m_state = txState;      // 1. set in RAM: effective on the NEXT tick
    this->m_loaded = true;        //    (a pending boot-load can no longer overwrite it)

    this->log_ACTIVITY_HI_TransmitStateSet(txState);   // 2. tell the ground

    if (!this->persistState(txState)) {                // 3. save for reboot survival
        this->log_WARNING_HI_StateFileWriteFailure();  //    save failed: warn +
        this->cmdResponse_out(..., EXECUTION_ERROR);   //    error response, BUT the
        return;                                        //    state change still stands
    }
    this->cmdResponse_out(..., OK);
}

4.4 Reboot persistence with corruption detection

Type: Feature    Verifies: TelemetryGate-4, TelemetryGate-5, TelemetryGate-6

The saved state is a few bytes in flash: the letters TGS1 (so a random file cannot be mistaken for a state file), the state byte, and an integrity byte that must be the exact bit-inverse of the state. Any single flipped bit fails the check:

// Components/TelemetryGate/TxStateCodec.cpp, the encode side
buffer[0..3] = 'T','G','S','1';        // magic: is this even our file?
buffer[4]    = state;                  // 0 = ENABLED, 1 = DISABLED
buffer[5]    = ~state;                 // integrity: must be exact complement

// decode: wrong magic, wrong length, state != ~integrity, or unknown
// state value  ->  CORRUPT  ->  default: ENABLED + warning event

A missing file is not treated as corrupt: first boot has no file and silently defaults to ENABLED (TelemetryGate-5). A damaged file raises StateFileCorrupt exactly once (TelemetryGate-6).

4.6 Adaptation for the washu fork: declaring the new telemetry channels

Type: Patch (build fix during the fork port)    Verifies: supports TelemetryGate-8 (makes the counters visible in downlink)

The washu fork runs a newer F´ that refuses to build unless every telemetry channel is assigned to a downlink packet. The first firmware build failed with exactly that error. The fix adds the gate's two channels to the Health and Status packet:

// ReferenceDeployment/Top/ReferenceDeploymentPackets.fppi
   packet HealthAuxiliary id 4 group 5 {
     ...
     CdhCore.tlmSend.SectionEnabled
+    telemetryGate.TransmitState
+    telemetryGate.GatedTicks
   }

After this one change the full firmware build passed (bootable.uf2 plus signed image).

4.8 Requirements schema upgrade and terminal editor

Type: Tooling    Serves: CDH-1 to CDH-31 and all L2 groups

Requirement tables gained Method, Level, Pass Criteria, Status, and Reason columns (old three-column tables still parse), the 105 CDR requirements were imported, and scripts/req.py edits any requirement from the terminal. The criteria-before-testing rule is enforced in code, not by convention:

6. Risks and open items

  • Hardware test pending. The over-the-radio enable/disable test exists. Run it on a board before treating CDH-3 as verified above Unit level.
  • A reset in the middle of the flash save can lose a commanded disable. By design the satellite then boots ENABLED (transmitting). Operators should re-check the state after any reboot during a quiet window.
  • "Command failed" does not mean "nothing happened". If the flash save fails, the error response is returned but the gate state did change in RAM. This is documented, but ops procedures should reflect it.
  • Almost all CDH requirements still have criteria = TBD. The matrix shows which of the 251 requirements have criteria, tests, and passing results (currently 8 automated, 8 passing). Deciding the remaining criteria is the next team task, one req.py set per requirement.
